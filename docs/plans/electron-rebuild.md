- Status: draft
- Adopted by: pending

## 目的

Godot版を参照実装として維持しながら、ゲームを Electron + React + TypeScript のデスクトップアプリとして再構築する。

最優先はレンダリング基盤の置換そのものではなく、編集データの扱いを正常化することである。現在は実行中の `TextureRect` の位置を、スタックトレース由来の `ファイル:行番号` と正規表現で GDScript へ書き戻している。これを、ID を持つストーリー・レイアウト・バトル設定データを唯一の正とする構成へ改める。画面、プレビュー、エディタ、保存処理が同じデータを読むようにする。

## 現状の整理

- Godot の画面・進行・編集機能は `Main.gd`（約 7,000 行）、`BattleScene.gd`（約 2,500 行）、`StoryScene.gd`（約 1,400 行）へ集中している。
- ストーリー章とバトル章は GDScript のクラス・継承・命令列として書かれており、データと実行処理が混在している。
- `SourceFileWriter.gd` と `Main.gd` は、ゲーム内エディタの編集内容をソースコードに直接反映する。位置の特定・書換えが行番号と正規表現に依存するため、表示調整が別の箇所を壊し得る。
- カード、グレード、セーブには既存のデータ表現があり、カード画像は Normal / Bronze / Silver / Gold / Platinum の15枚が揃っている。
- 1920×1080 を基準に作られた演出とレイアウトが多い。移植時に画面基準を明示しないと見た目が崩れる。

## 採用する構成

Electron をデスクトップ・ランタイム、React を画面構築、TypeScript をゲームロジックとコンテンツ定義に使う。Electron のメインプロセスはウィンドウ、ファイル、セーブだけを担い、レンダラーには狭い API だけを公開する。

```text
electron/
  main/           ウィンドウ、保存、ファイルアクセス、IPC検証
  preload/        contextBridge 経由の限定API
  renderer/       React画面、ゲーム表示、共有表示部品
  editor/         開発用エディタの画面と編集機能（別ビルド）
packages/
  domain/         純粋なカード・デッキ・勝敗・進行・セーブロジック
  content-schema/ コンテンツ型、スキーマ、検証器
content/
  stories/        会話・分岐・演出命令
  battles/        相手、デッキ、報酬、ランダム遭遇設定
  layouts/        立ち絵・UIの位置、拡大率、反転など
  catalog/        キャラクター、カード画像、音声等のID対応表
assets/           既存画像を移管した配布用アセット
```

ストーリー命令は例えば `{ id, type, args }`、配置は `{ id, portrait_id, side, x, y, scale, flip }` のようなシリアライズ可能な形式にする。参照はすべて安定した ID で行い、ソースの行番号・UIノード名・正規表現を編集対象の識別子にしない。

開発用エディタは同じコンテンツ文書を編集し、プレビューはその場の一時状態を描画する。保存時はスキーマ検証後に一時ファイルへ書き、置換前バックアップを残す。通常ゲームと開発用エディタは共有データ・表示部品を使う別ビルドとし、通常ゲームの成果物には編集画面、編集用IPC、専用依存関係・アセットを含めない。

画面は1920×1080を基準に縦横比を維持して拡大・縮小し、ウィンドウの比率が異なる場合は上下または左右に余白を設ける。コンテンツの正本はJSONに統一する。

## 対象範囲

- Electron デスクトップ版の土台、React UI、TypeScript のゲームドメインを作る。
- 既存のストーリー、バトル、ミニゲーム、カード、グレードをデータ駆動へ移し、Electron版の新規セーブを実装する。
- 立ち絵・カード・UIの位置を、コードを書き換えず編集・保存・再読込できるようにする。
- Matilda のチュートリアルを最初の完全な縦切りとして移植する。
- Godot版と並行して動作確認できる移行期間を設け、既存アセットを引き継ぐ。Godot版の既存セーブはElectron版へ移行しない。

## 対象外

- 移行と同時の新ストーリー、新カード効果、バランス全面調整、画像の描き直し。
- Web版、モバイル版、オンライン同期・クラウドセーブ。
- Tauri版の同時開発。
- Linux版と、Godot版セーブデータの読込・変換。
- Godot版の即時削除。完全移行を確認するまで参照実装として残す。

## 段階的な実施計画

### 0. 移行前の棚卸しと基準固定

1. 現行の画面、ストーリー命令、バトル種別、ミニゲーム、編集機能、セーブ項目、アセットを一覧化する。
2. Matilda チュートリアル、通常バトル、ランダムバトル、セーブ・ロードを基準シナリオとして記録する。
3. Windowsを主対象、macOSも動作対象とし、1920×1080の固定アートボードを縦横比維持で拡大・縮小する方針を記録する。
4. この段階では既存 Godot の振る舞いを変えず、移植対象と優先順位だけを固定する。

### 1. Electronの基盤と境界を作る

1. Electron、React、TypeScript のワークスペースを追加する。
2. メインプロセス、preload、レンダラー、純粋ドメイン、コンテンツスキーマを分離する。
3. `contextIsolation` と sandbox を有効にし、通常ゲームにはセーブ読込・保存など必要最小限のIPCだけを公開する。開発用コンテンツ読込・保存はエディタビルドに限定する。
4. メインプロセス側で IPC 引数、保存先、コンテンツのスキーマを検証する。レンダラーから任意パスの読み書きは許可しない。
5. WindowsとmacOSで最小のウィンドウとタイトル画面を起動し、通常ゲームと開発用エディタの別ビルドの入口を設ける。

### 2. データモデルを定義し、コンテンツを分離する

1. カード、グレード、デッキ、勝敗、報酬、プレイヤー状態、セーブの TypeScript 型と JSON スキーマを定義する。
2. ストーリーを会話、立ち絵、位置、選択肢、画面遷移、バトル開始などの宣言的な命令へ分ける。
3. バトル章の継承クラスは、相手・デッキ・報酬・特殊ルールを持つデータレコードへ置換する。
4. 既存の GDScript コンテンツから機械的に抽出できる静的な項目は移行補助ツールで取り出す。条件分岐や任意コードの解釈を正規表現だけで自動変換しない。
5. 以後の新規コンテンツは JSON を正とし、コードの直接書換えを禁止する。

### 3. Matildaチュートリアルを縦切りで完成させる

以下を一本の流れとして Electron版に実装し、以後の移行の雛形にする。

1. 新規ゲーム開始、会話、立ち絵、Matilda の説明を表示する。
2. Normal のグー・チョキ・パー、グレード表示、デッキ・手札・勝負表示を再現する。
3. じゃんけん判定、引分時のグレード判定、進行状態の保存・再開を実装する。
4. 開発用レイアウトエディタで立ち絵やカード表示を選択・移動・保存し、再起動後も同じ位置で表示されることを確認する。
5. この縦切りが Godot版の基準シナリオを通過するまで、章全体の一括移植へ進まない。

### 4. 主要コンテンツとゲームフローを拡張する

1. ストーリー章を依存順に移し、共通命令・共通UIを先に増やす。
2. 固定バトル、ランダムバトル、相手デッキ、報酬をデータから生成する。
3. グレード配布・カード保有状況のゲームバランスは、移植後にデータだけで変更できるようにする。
4. タイトル、ロード、画面遷移、所持カード、カードボックス、デッキ編集を実装する。
5. ミニゲームの共通フローをストーリー進行に組み込む。現行の全ミニゲームと必要な補助画面は、標準版への切替前に移植する。

### 5. 全体の品質保証・公開準備・切替を行う

1. Electron版の新規セーブに `save_version` を導入し、保存・再開と将来の版更新に備える。Godot版の既存セーブには触れない。
2. コンテンツ検証コマンドを作り、ID重複、欠落アセット、壊れた遷移、無効なデッキ・カードをビルド前に検出する。
3. Godot版と Electron版の基準シナリオを並行確認し、差分をチケット化して解消する。
4. 全ストーリー・ミニゲームを含む必須シナリオ、Electron版の保存・再開、WindowsとmacOSでの配布確認を終えた後にElectron版を標準版とする。
5. Godot版の保管・廃止は、標準版切替後に別途判断する。アセットと履歴を先に削除しない。

## 検証方針

- `domain` の単体テストで、じゃんけん勝敗、引分時のグレード比較、デッキ制約、報酬、Electron版セーブの保存・再開を検証する。
- コンテンツスキーマのテストで、全ストーリー・バトル・アセット参照を検証する。
- Playwright 等のUIテストで、Matilda チュートリアルの開始から勝負、セーブ、再開までを確認する。
- 開発用エディタの回帰テストで、配置を編集して保存・再読込しても同じレコードだけが更新され、GDScript を変更しないことを確認する。
- 1920×1080の代表画面はスクリーンショット比較を行い、カード・立ち絵・会話UIの大きさと重なりを確認する。
- 異なる縦横比の画面では、画面全体を縦横同率で拡大・縮小し、残る領域に余白を設けることを確認する。
- Godot版を廃止する前に、主要ストーリー、固定バトル、ランダムバトル、全ミニゲーム、Electron版の保存・再開を手動でも通す。

## 主なリスクと対策

| リスク | 対策 |
| --- | --- |
| 全面移植が長期化し、遊べる状態にならない | Matilda の縦切りを最初の到達点とし、以後は機能単位で移す。Godot版を並行維持する。 |
| GDScript内の暗黙の分岐を見落とす | 基準シナリオを先に記録し、静的に変換できない箇所は明示的なデータ設計へ手で移す。 |
| UIの見た目がGodot版からずれる | 基準解像度、フォント、アセット表示ルールを早期に固定し、代表画面を画像比較する。 |
| 新規セーブが壊れ、進行状態を失う | 版番号と保存・読込の検証を設け、失敗時に既存のElectron版セーブを壊さない。 |
| Electronのレンダラーがローカルファイルへ過剰にアクセスする | context isolation、sandbox、限定IPC、メイン側の入力・パス検証を採用する。 |
| 配布アプリへ開発用編集機能が混入する | 通常ゲームと開発用エディタを別ビルドにし、通常ゲームの成果物に編集画面・編集用IPC・専用依存関係やアセットがないことを検証する。 |

## 検討した代替案

1. **Godotを維持してデータ駆動化だけ行う**
   - 移行コストは小さいが、現在感じているUI編集・画面構築の摩擦を残す。Electron再構築の目的を満たしにくいため採用しない。
2. **Tauri + Reactで再構築する**
   - Reactは利用でき、配布サイズやネイティブ側の安全性では利点がある。一方でRust層の実装・保守とOS WebView差分が増える。まずはChromiumを同梱して描画差が小さく、Nodeで既存資産の移行補助を書きやすいElectronを採用する。
3. **Godot版を止めて一括で作り直す**
   - 比較対象と遊べる版を失い、仕様漏れの発見が遅くなるため採用しない。

## 確定した移行方針（タスク0.3）

1. Windowsを主対象とし、macOSでも動作させる。Linuxは初回対象外とする。
2. 1920×1080の固定アートボードを縦横比維持で拡大・縮小し、比率が異なるウィンドウでは余白を表示する。
3. ストーリー、バトル、レイアウトなどのコンテンツ形式はJSONに統一する。
4. 開発用エディタは通常ゲームと別ビルドにし、通常ゲームの成果物へ編集機能を含めない。
5. Godot版の既存セーブは移行しない。Electron版は新規セーブから開始し、既存のGodot版セーブファイルを削除・上書きしない。
6. 現行のミニゲームはゲーム本体の必須要素であり、Electron版完成の条件にすべて含める。Matildaの縦切りは開発中の検証地点であり、完成版の機能削減ではない。
7. 配布方式、自動更新、コード署名の詳細はゲーム本体が完成してから公開準備段階で決める。WindowsとmacOSでの動作確認は開発中から行う。

## 実装開始時の最初の成果物

最初の実装タスクは「Electron基盤 + コンテンツスキーマ + Matildaチュートリアルの縦切り」に限定する。この時点で、ゲーム画面の配置を編集してもソースコードの行番号や正規表現に依存せず、データファイルの対象IDだけが更新されることを受け入れ条件とする。
